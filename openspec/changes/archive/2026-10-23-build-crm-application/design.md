# Design

## Context

This is a greenfield, self-hosted CRM built in an empty repository. See `proposal.md` for motivation and the seven delta specs under `specs/` for required behavior. The deployment serves one team workspace, all active members share the same CRM data, and no external email or calendar service is available. Local development and production both use PostgreSQL; local Postgres runs through Docker Compose.

## Goals / Non-Goals

**Goals:**

- Deliver one deployable Next.js application backed by PostgreSQL, with no separate API service.
- Keep authentication, authorization, and validation authoritative on the server.
- Preserve history through archive semantics and recorded authorship rather than destructive deletes.
- Make each implementation phase independently runnable and testable.
- Keep the data model ready for future growth without implementing multi-tenancy now.

**Non-Goals:**

- Multiple workspaces, tenant isolation, or per-record sharing.
- Multiple currencies, FX conversion, tax, or invoicing.
- Email/calendar sync, campaign delivery, file attachments, or customer-facing portals.
- Background job processing, realtime updates, or webhook delivery.
- Business-hours or timezone-aware SLA calculations.
- Public APIs, mobile applications, custom report builders, and audit logs.

## Decisions

### Application architecture

- **Next.js 15 App Router with React 19 and strict TypeScript.** Server Components perform reads directly through Drizzle; Server Actions perform mutations. Route Handlers exist only for the Auth.js endpoints, a read-only global search endpoint, and a health check. This avoids a redundant REST layer for an app whose only client is its own UI.
- **Route groups** separate `(auth)` pages (setup, sign-in, invite acceptance, password reset) from `(app)` pages that require a session. `(app)/layout.tsx` renders the navigation shell and calls `requireUser()`.
- **No global client data store.** Server Components own fetched data; URL search parameters own list filters and pagination; `revalidatePath` refreshes views after mutations. Interactive widgets use local state and `useOptimistic` where useful.
- **Validation with Zod** in a shared module. Client forms use `react-hook-form` plus the same schemas for immediate feedback, while every Server Action re-validates independently. Server-side validation is the source of truth.
- **UI built from shadcn/ui and Tailwind CSS v4.** Radix primitives provide keyboard and focus behavior. Client components are limited to forms, tables with client interactions, the Kanban board, charts, command search, and date rendering.

Alternatives considered: a separate REST or tRPC API adds ceremony without a second consumer; a client-side query cache duplicates Server Component state. Both are deferred until a concrete need appears.

### Database and schema

- **PostgreSQL 16 via Docker Compose, Drizzle ORM, `postgres.js`, and drizzle-kit migrations.** Drizzle keeps schema and query types aligned with TypeScript while allowing SQL aggregates for dashboard metrics.
- **Primary keys are UUIDs** generated by `gen_random_uuid()`. Timestamps use `timestamptz`; amounts use `numeric(14,2)`; date-only fields use `date`. Enums are PostgreSQL enums for roles, statuses, activity types, priorities, and channels.
- **One workspace, no `workspace_id` columns.** All active members see all records. This is the largest structural assumption in the design; supporting multiple workspaces later requires adding a workspace table, backfilling a workspace id into every record, and enforcing scoping in every query.

Core tables:

| Area | Tables | Key constraints |
| --- | --- | --- |
| Access | `users`, `invites`, `password_reset_tokens`, `login_attempts` | Unique `lower(email)`; token digests are unique and single-use; role and status enums; `session_version` on users |
| Directory | `companies`, `contacts`, `tags`, `company_tags`, `contact_tags` | Contact email unique per workspace ignoring case; owner foreign keys; `archived_at` on companies and contacts |
| Sales | `pipelines`, `stages`, `deals` | One default pipeline; stage outcome enum; `amount >= 0`; stage belongs to pipeline and contact belongs to company, enforced in the service layer |
| Engagement | `activities`, `tasks` | Five nullable record links plus a check requiring at least one; `activities.type` includes `stage_change`; tasks have nullable assignee and completion fields |
| Support | `tickets`, `ticket_comments` | Status and priority enums; requester contact required; company derived through the requester; comment visibility enum |
| Marketing | `segments`, `campaigns`, `campaign_recipients` | Validated JSON criteria; segment snapshot JSON on campaigns; unique `(campaign_id, contact_id)`; engagement status enum |

- **Record links use nullable foreign keys, not polymorphic IDs.** `activities` and `tasks` each have nullable `company_id`, `contact_id`, `deal_id`, `ticket_id`, and `campaign_id` columns. A check constraint using `num_nonnulls(...) >= 1` enforces at least one link. This preserves referential integrity and lets each detail page query its own indexed column.
- **Stage changes are system activities.** A deal stage move writes an `activities` row with `type = stage_change` and a `metadata` JSON payload containing the previous and next stage IDs. These entries share the existing timeline instead of requiring a separate union query.
- **SLA due times are derived, not stored.** Ticket due times are computed from `created_at` and the priority target, so changing priority automatically recalculates them. Only `first_response_at`, `resolved_at`, and `closed_at` are persisted.
- **Search uses `pg_trgm` GIN indexes** on company name/domain, contact name/email, deal name, and ticket subject. Global search and directory search use parameterized `ILIKE` queries with these indexes. If the extension is unavailable, the queries still work with sequential scans, but the migration expects the Docker Postgres image to provide it.
- **Archive instead of delete** for companies, contacts, segments, pipelines, and stages. Deals and tickets retain history through status rather than deletion. Activities and tasks support explicit deletion because they are user-authored working records.
- **Initial migration seeds the default "Sales Pipeline"** with its six stages, so the application has a usable pipeline immediately after `db:migrate` without requiring a seed command. The seed script adds demo data only in development.

### Authentication and session model

- **Auth.js v5 Credentials provider with JWT session cookies.** Passwords are hashed with Argon2id. Sessions use an HttpOnly, SameSite=Lax cookie, `Secure` in production, with a seven-day sliding lifetime. Auth.js supplies the sign-in flow, CSRF protection, and cookie handling that a custom session table would otherwise require.
- **Revocation is handled by a database check, not by trusting the JWT.** `requireUser()` verifies the session token, loads the user row, and rejects the request when the account is inactive or when the token's `sessionVersion` no longer matches `users.session_version`. `requireAdmin()` builds on it. Every protected layout, Server Action, and Route Handler calls one of these helpers, so deactivation and password changes take effect on the next request even though the JWT remains cryptographically valid.
- **First-run setup is serialized.** Setup runs in a transaction that takes a fixed PostgreSQL advisory lock, checks that no users exist, creates the first admin, and creates the default pipeline if it is missing. A unique email index is the final guard against concurrent setup requests.
- **Invitations and password resets use single-use tokens.** The server generates 32 random bytes, returns the raw URL-safe token once to the administrator, and stores only its SHA-256 digest with an expiry and nullable acceptance/use timestamp. Invitations expire after seven days and resets after 24 hours. Redemption happens in a transaction that marks the token used and creates or updates the account.
- **Sign-in throttling is database-backed** through `login_attempts`, keyed by normalized email. Five failures within 15 minutes lock that email for 15 minutes; a successful sign-in clears the row. Responses remain generic to avoid email enumeration.
- **No email verification or self-service forgot-password flow.** Both require message delivery, which is out of scope. Administrators share invite and reset links out of band.

Alternative considered: a custom database-session implementation gives immediate revocation without a per-request user load, but requires reimplementing CSRF and cookie handling. The database check is simpler and fast enough for a small team.

### Domain workflows

- **Deal stage moves run in a transaction.** The service validates that the target stage belongs to the deal's pipeline, honors the lost-reason requirement, updates stage/status/closed fields, and inserts a `stage_change` activity. A move uses optimistic concurrency: the client submits the deal's `updated_at`, and the update fails with a conflict message when another member changed the deal first.
- **Deal status is never edited directly.** It is recalculated from the stage outcome on every stage change. Reopening clears `closed_at` and `lost_reason`.
- **Pipeline administration validates removal.** Stages containing deals and the default pipeline cannot be archived or removed. Reordering rewrites all stage positions in one transaction.
- **Ticket status transitions follow an explicit state machine** matching the support spec. Setting resolved records `resolved_at`; reopening clears it and `closed_at`. Comment creation and the first-response timestamp happen in the same transaction; only a reply by a team member sets the first-response time, not an internal note.
- **SLA targets live in one policy module.** First response and resolution hours are keyed by priority and measured in calendar hours from creation in UTC. The UI formats timestamps in the viewer's local timezone, but overdue calculations use UTC. This is deliberate for the MVP and documented as a non-goal for business-hours SLAs.
- **Segments are evaluated as live queries.** A validated criteria object is translated into a Drizzle query: AND across fields, OR within the tag list, archived contacts excluded. The count shown in the UI and the audience created at activation use the same evaluator.
- **Campaign activation snapshots the audience and segment metadata in one transaction.** Recipients start as `targeted`, and later segment or contact changes do not alter the audience. Archived campaigns reject all writes.
- **CSV import is synchronous and bounded.** A Server Action accepts the file and mapping, rejects files over 5 MB or 5,000 rows before parsing, parses with Papa Parse, validates every row, resolves contact companies by domain then exact name, and inserts valid rows in batches. Invalid rows and duplicates are skipped and returned as a row-numbered report. Contacts whose company cannot be resolved are skipped with an explanatory error so users import companies first.
- **Global search is a read-only GET Route Handler.** It requires a session, returns grouped results capped at five per type, and never mutates data. Server Actions handle all writes.

### UI structure

- **Persistent shell:** a sidebar with Dashboard, Companies, Contacts, Deals, Tickets, Campaigns, Tasks, and Settings; a top bar with global search and the user menu. The sidebar collapses into a sheet at mobile widths.
- **List pages** use server-rendered tables with URL-driven search, filters, sorting, and pagination, so views are shareable and back-button friendly.
- **Detail pages** use a header with key fields and actions, followed by tabs for overview, timeline, tasks, and related records. Related-record lists reuse the same table components as their primary list pages.
- **Kanban board** uses dnd-kit for drag-and-drop plus a per-card move menu for keyboard users. Moves update optimistically and reconcile or refresh on conflict.
- **Dashboard** aggregates metrics in SQL and passes numbers to Recharts client components. Personal task metrics come from the signed-in user; all other metrics are workspace-wide.
- **Dates** are stored in UTC. A small client component renders timestamps in the viewer's local timezone. Date-only task due dates are evaluated against UTC dates, which is acceptable for the MVP and recorded as a limitation.
- **Empty and error states** are designed per page: zero-value metrics link to the relevant create action, empty tables explain the next step, and failed Server Actions return field or form-level errors.

### Security and data integrity

- Every Server Action validates the session, checks role permissions, validates input with Zod, and verifies that referenced records exist and belong together. Client-supplied IDs are never trusted as authorization.
- State-changing operations are never exposed as GET requests. Auth.js and Server Actions provide CSRF/origin protection.
- User-provided text is rendered as plain text; no raw HTML rendering is allowed. Drizzle parameterizes queries, and raw SQL is restricted to aggregates with bound values.
- Passwords are never logged or returned. Token digests are looked up directly; raw tokens exist only in the one-time link.
- Archived records remain readable but cannot be selected for new relationships. Foreign keys prevent dangling references.
- No audit-log table in this version. Authorship and timestamps are captured on records, comments, activities, and stage changes.

### Testing and quality

- **Vitest unit tests** cover normalization (emails, domains, tags), ticket state transitions, SLA calculations, segment criteria translation, CSV row validation and deduplication, weighted pipeline math, and campaign metric math.
- **Integration tests** run against a dedicated `crm_test` PostgreSQL database. Migrations are applied once, each test runs in a transaction or truncates affected tables, and services are exercised through their public functions with real SQL constraints.
- **Playwright end-to-end tests** cover first-run setup, invite acceptance, sign-in throttling behavior (with a test clock or reset hook), company/contact CRUD, deal movement and win/loss, ticket lifecycle and comments, campaign activation and engagement updates, dashboard metrics, and global search.
- **Static checks:** strict TypeScript, ESLint, Prettier, and `drizzle-kit check` run in the quality script alongside tests.
- **Seed data** lives in a development-only script and creates users, companies, contacts, deals, tickets, and campaigns without hard-coded production credentials.

### Deployment and operations

- Required environment variables: `DATABASE_URL`, `AUTH_SECRET`, `AUTH_URL` (or `APP_URL`), and `NODE_ENV`. `AUTH_TRUST_HOST=true` is set for self-hosted deployments.
- Docker Compose provides PostgreSQL for local development. A multi-stage Dockerfile builds the Next.js standalone output for production.
- Migrations run with `drizzle-kit migrate` before the application starts. The initial migration inserts the default pipeline. Production starts with an empty user table and completes first-run setup.
- A `/api/health` Route Handler checks database connectivity for container health checks.
- Rollback for this greenfield release is a database restore from backup; migrations are forward-only. Development environments can reset with `docker compose down -v` and a fresh migration.

## Risks / Trade-offs

- **Large single change** → Implementation is split into six phases with a runnable application after each phase; tasks are grouped by phase and each phase has a verification checkpoint.
- **JWT sessions require a per-request user lookup for revocation** → One indexed primary-key read per protected request is acceptable for a small team and avoids stale permissions after deactivation.
- **Single workspace is baked into the schema** → Adding multi-tenancy later requires a workspace table, `workspace_id` backfill, query scoping, and likely row-level security; this is explicitly deferred.
- **USD-only amounts** → Dashboard totals remain correct without FX handling; multi-currency becomes a separate change if needed.
- **Calendar-hour SLAs in UTC** → Tickets near midnight or outside business hours may be marked overdue sooner than a business-hours policy would; documented as a non-goal.
- **Fixed campaign audience** → Contacts who match later are not added, matching the snapshot requirement; users create a new campaign to reach them.
- **Internal notes visible to admins and the current assignee** → Reassigning a ticket exposes earlier internal notes to the new assignee; this is acceptable for a small trusted team.
- **Synchronous CSV import** → A 5,000-row file may take several seconds; the size limit and batching keep memory bounded, and a background import job can replace it later.
- **Trigram extension dependency** → The Docker Postgres image includes `pg_trgm`; deployments without it lose index acceleration but not search correctness.
- **Optimistic concurrency only on deals and tickets** → Other records use last-write-wins, which is acceptable for a small team; the conflict pattern can be extended later.
- **No email delivery** → Invitations, resets, and campaign outreach are manual; this is a deliberate scope boundary, not a temporary implementation detail.
- **UTC date-only tasks** → Users far from UTC may see a task's due date shift near midnight; a workspace timezone setting is a future change.
- **No audit log** → Authorship and timestamps cover the MVP's accountability needs; regulated environments would require a dedicated audit trail.

## Migration Plan

1. Initialize the repository with the Next.js application, Docker Compose Postgres, environment templates, and Drizzle configuration.
2. Apply the initial migration, which creates the schema and seeds the default Sales Pipeline.
3. Start the application, complete first-run setup, and verify that the admin can invite a member.
4. Run the development seed only in non-production environments for demo data.
5. Deploy by running migrations, building the standalone Next.js output, and starting the server behind HTTPS. Back up the database before later migrations; this release has no existing data to migrate.
6. Roll back a failed deployment by restoring the pre-deployment database backup and redeploying the previous application image. Migrations are not automatically reversed.
